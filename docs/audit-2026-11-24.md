# PortableDev v2 文档审阅：硬性缺陷清单 + 总体架构报告

> 审阅对象：`docs/` 下 7 份文档（architecture / spec / commands / kernel / package-spec / index-spec / window），共 3542 行。
> 审阅方式：逐份通读 + 交叉比对 + 跑 `tools/check_docs.py`。
> 结论口径：**硬性缺陷** = 两份文档对同一件事给出不同答案，或同一份文档内部自相矛盾，按任意一种理解实现都会在另一端被推翻。

---

## 0. 一句话结论

骨架是好的：微内核 + 租界 + 账本/存档点 + 路径即身份，这套组合能撑住"拔盘恢复原样"的目标。
审阅时**协议与状态机的边界处有 15 处硬矛盾**，其中 6 处属于"必须先定，否则写不出可工作的第一版"（租界发起方、store 路径由哪个哈希决定、intent 存在哪、退出码空间、pd 解不解析参数、ui 从哪来）。
**2026-11-24 更新**：D1/D2/D3/D4/D5/D6/D7/D8/D9/D10/D11/D12/D13/D15 已按裁决改完，参数表补全，`check_docs.py` 增加了开关闭合与退出码唯一两项检查；改动清单见 §6，第二轮（G1–G12、D14）的裁决与理由见 §7。

当时 `check_docs.py` 报"✓ 没有发现不一致"，但它只检查链接 / 命令名 / 错误码 / 退出码数字 / 文件名引用，**语义冲突一个也查不到**——这正是下面 15 条当时全部漏网的原因。

## 1. 硬性缺陷（P0：互相矛盾，必须先裁决）

### D1 租界的发起方：内核发 vs 存储扩展发 ★最严重

| 位置 | 说法 |
|---|---|
| `spec.md:606`、`spec.md:617` | `ext.invoke` 里由**内核**带上 `grants: [...]`，并注明"grants 是存储扩展发下来的租界" |
| `spec.md:640` | "内核只是转发，**决定权在存储扩展**" |
| `architecture.md:829`、`architecture.md` 3.1 | "租界由存储扩展发，不由内核发；**内核连 store 在哪都不知道**" |
| `architecture.md:231`（4.4 流程） | 扩展自己"申请 → 存储建目录 → 返回路径"，全程没有内核参与 |

**矛盾**：派活时内核要先在 `ext.invoke` 里塞 grants，就意味着**内核必须先向 storage 申请并持有租界目录路径**——这直接违反"内核不碰盘、不知道 store 在哪"这条被写进决策记录（`architecture.md:829`）的核心约束。
**后果**：内核要么破例持有存储路径（微内核边界失效），要么 `ext.invoke` 的 grants 字段永远是空数组（协议字段与实现不符）。
**建议**：二选一并写死。推荐改协议：`ext.invoke` 不带 grants，扩展启动后第一条 `ctl` 就是 `grant.request`；内核只做无状态转发。若坚持预发，则必须承认"内核持有租界句柄"，并同步删掉 3.1 与决策记录里那两句话。

### D2 `idleTimeout` 一词三义，默认值两个

| 位置 | 语义 | 默认 |
|---|---|---|
| `spec.md:77`、`spec.md:209` | 扩展**进程空闲退出**（无在途请求多久后退出） | `5m` |
| `spec.md:645`（5.5） | **消息看门狗**（无任何消息 → 内核发 ping → 再超时强杀） | `30s` |
| `spec.md:558`（4.7） | 客户端侧"**30s 无事件且无心跳 → 判定卡死**" | 30s |

**矛盾**：同一个键既是"进程生命周期"又是"看门狗阈值"，且默认值 5m 与 30s 并存；`ext.json` 的 `lifecycle.idleTimeout` 到底喂给谁没有定义。
**后果**：扩展 5 分钟才退出 vs 30 秒被 ping；实现者必然按一个写、按另一个测，行为不可预期。
**建议**：拆成三个键——`lifecycle.idleTimeout`（进程回收，5m）、`lifecycle.heartbeatTimeout`（看门狗，30s）、`client.watchdog`（客户端侧），并明确"看门狗 < 进程回收"。

### D3 退出码空间已经破裂（三处冲突叠加）

1. `commands.md:33`：`--timeout <dur>` → 退出码 **24**；
   `commands.md:58`：退出码 **24** = 依赖未满足。**同一个码两个含义**。
2. `commands.md:339`：`pd run` / `pd shell` 的退出码 = **被启动程序的退出码原样透传**。于是 `pd run foo` 返回 12 时，调用方无法区分"foo 自己返回 12"还是"断言失败"；`pd run` 的 0 也可能是被启动程序的 0 而不是 pd 的成功。
   `commands.md` §3 又规定"成功只有 0，批量操作返回第一个失败的退出码"——这条契约在 `run`/`shell` 上不成立。
3. `commands.md` 5.15：`pd log --follow` 取消返回 **0**；而全局规则是取消 = **130**（`commands.md` §3、`spec.md` §4.7 一致要求 `ERR_CANCELLED`）。

**后果**：shell 脚本、CI、窗口壳都无法仅凭退出码判断成败；`--json` 之外的机器契约失效。
**建议**：确立"退出码 = pd 自身结果"的单一语义，被启动程序的退出码放进 `done.metrics.childExitCode` 或 `pd run --propagate` 显式开关；`--timeout` 单独分配一个码（如 25）；`--follow` 的取消统一为 130（或显式写为文档级例外，并在 §3 表里标注）。

### D4 `pd` 到底解不解析参数

- `commands.md:15`：`pd` 把参数**原样**转给内核，"自己不解析"；`architecture.md` 3.7/3.8 同义反复强调。
- `commands.md` §2：`--json`、`--no-color`（渲染）、`--root`（选盘/连哪个管道）、`--quiet`、`--trace`——**这些必须由 `pd.exe` 自己解析**，否则无法决定连哪根管道、输出怎么渲染。

**矛盾**：`--root` 尤其致命——管道名是 `\\.\pipe\portabledev-<stickId>`（`spec.md:310`），`pd` 不解析 `--root` 就不知道 stickId。
**建议**：明确"壳只解析**连接类与呈现类**全局开关（`--root`/`--json`/`--no-color`/`--quiet`/`--trace`），其余 argv 原样透传"，并把开关清单标为"壳层开关"与"内核开关"两类；同时补上 `stickId` 的生成规则（是盘序列号哈希？锁文件里的值？——现在三份文档都在用，没有一份定义）。

### D5 `ui` 扩展从哪来、装到哪：三处互斥

- `window.md:217`：没装界面时按钮调 `pd install ui`，**装完后 `app\extensions\` 里出现 `ui` 扩展**。
- `kernel.md:32`：`app\` **只读**，"升级只换目录内容，不在这里存任何用户数据"；用户扩展在 `v2\extensions\`。
- `architecture.md` 5.1 / `package-spec.md` 0：**包永远不带界面**，界面只属于扩展；`pd install` 装的是包（进 `store\`）。

**矛盾**：`pd install ui` 若走包通道，产物是 `store\<hash>-ui-<ver>`，既不在 `app\extensions\` 也不提供 pages；若走扩展通道，命令应是 `pd ext update`（`commands.md` 5.17），而 `pd install ui` 不是扩展安装命令。
**建议**：把 `ui` 定义为**内置扩展**（`app\extensions\ui`，随程序发布，只读），窗口壳的"安装"按钮改为"启用内置 ui 扩展"或 `pd ext enable ui`；若要允许第三方 UI 扩展，则新增 `pd ext add <目录|zip> --from <源>` 并明确它不进 `app\`。

### D6 store 路径由哪个哈希决定：流程与规则表冲突

- `architecture.md:457`（6.1 表）+ `package-spec.md:380`（3.13）：**有 `source.sha256` 的包用压缩包哈希**决定路径（安装前就知道）；只有 `files\` 的用 `.pdpkg` 哈希；包目录用目录指纹。
- `architecture.md:508`（第 8 节流程第 7 步）：无条件"**算指纹 → 决定 store 路径**"。

**矛盾**：同一条流程里，路径的决策依据前后不一致；而 `architecture.md:673`（11.2 intent）又要求 rename **之前**写 `intent{target=<store路径>}`——如果路径要等解压+算指纹才知道，`intent` 的 target 在 begin 阶段根本填不出来。
**后果**：崩溃恢复的目标路径与实际 rename 目标可能不同 → 恢复逻辑误判（"目录在/不在"）。
**建议**：明确"target 在**解压前**确定"（archive 哈希 / pkg 哈希两条路），目录指纹只作为**校验值**写进记录；开发模式（无 `.pdpkg`）则先落 `staging`、指纹算出后再补写 `intent{target}`，并把这条写进 11.2 的第 1、2 步之间。

### D7 `intent` 存在哪：账本里 vs 独立文件

- `architecture.md:421`（6 节布局）：`state\intent\<任务号>.json`。
- `kernel.md:186`（5.2 恢复第 1 步）：扫 `state\intent\*.json`。
- `architecture.md:672`（11.2）："**账本写 intent** `{task, pkg, target, 阶段=begin}`"，阶段值 `begin → renamed → done`。

**矛盾**：一份说 intent 是独立 JSON 文件、按目录扫描；另一份说 intent 是账本（`ledger\*.jsonl`）里的行。两套存储的原子性、恢复顺序、清理方式都不同。
**建议**：统一为"**独立文件 + 阶段字段原地更新**"（`state\intent\<task>.json`，含 `phase: begin|renamed|done`），账本只记可撤销的接线改动，并以 `task` 号关联——这样 `kernel.md` 5.2 的扫描顺序才成立。

### D8 版本范围语法与命令行开关不自洽

- `spec.md:182`：范围语法"**只支持三种比较符** `>=` / `<` / `==`"，"解析不了 → 视为不匹配"。
- `index-spec.md:196`：`pd install firefox@^139`（caret 运算符，映射为 `>=139 <140`）。
- `index-spec.md:171`：流程第 5 步出现 `--pin` 开关；`commands.md` 全文没有 `--pin`（4.2 表与 5.1 细节都没有）。
- `package-spec.md:274`：`--no-scripts` 开关；`commands.md` 同样没有。

**后果**：(a) 严格按 spec 的解析器会把 `^139` 判为不匹配（用户敲了就报错）；(b) 两个被引用的开关无处注册，`pd help` / 补全 / 参数校验都覆盖不到。
**建议**：语法扩到 `^ ~ >= <= < > ==` 五种并给统一解析函数（或删掉 `^139` 示例）；`--pin`、`--no-scripts`、`--allow-scripts`、`--source` 全部补进 `commands.md` 4.2 表与 5.1 细节，让 `check_docs.py` 能查到。

### D9 兼容策略：拒绝 vs 尝试加载

- `architecture.md:706`（§12）：旧版读到新版格式 → **直接拒绝**并提示升级，"不猜"。
- `spec.md:302`（2.11 规则 5）：扩展可以声明比内核新的 `schema`，**只要 `requiresKernel` 满足就尝试加载**。

**矛盾**：`ext.json` 本身也是"带 schema 的格式文件"，两条规则直接对撞。
**建议**：区分"**状态文件**（记录/索引/配置）旧版遇新版必须拒绝"与"**声明文件**（ext.json / package.json）按 `requiresKernel` 决定、未知字段忽略"。两句话各改一处措辞即可。

### D10 环境变量与凭据：全量传 + 不打码，但同时"日志一律不写"

- `spec.md` 5.7 / `spec.md:681`：`ctx.env` 全量快照（含 `GITHUB_TOKEN`、代理口令），"现阶段**不做打码、不做白名单**"。
- `kernel.md:266`：日志"**环境变量一律不写进日志**，连键名也不写——在加密做出来之前，这是硬约束"；例外只有 `--trace-env` 写独立临时文件。
- `architecture.md` §17.1：结论仍是"全量传，日志加密以后做"。

**矛盾**：一处说"加密以后再收紧"，另一处已经把"不写日志"当成硬约束实现；而 `log.encryption` 在 `kernel.md` 2.1 里默认 `none`（加密还是预留）。三处对"现阶段到底怎么处理凭据"给出三种答案。
**建议**：写成一条可验收的规则链：进程序内存 → 允许；进事件流 `ctx.env` → 允许（本机管道）；进日志 → 禁止；进 `--json` 输出 → 禁止（默认）。并把 `--trace-env` 的临时文件位置、生命周期、是否加密写清。

### D11 账本切分粒度写错

`architecture.md:595`：正文说"账本**按天**切文件"，括号里的示例却是 `ledger\2026-11.jsonl`（**按月**）；`architecture.md:421` 布局写的是 `ledger\<yyyy-mm>.jsonl`。
**后果**：恢复时"按时间正序拼接"的实现会按天/按月两套逻辑分叉；跨月崩溃的恢复测试写不出来。
**建议**：改为"按月切分"（与文件名、与 50 档存档点的量级匹配）。

### D12 `persist` 与 `data.link` 的"方向相反"是错的

`package-spec.md:372`：`persist` 是"安装目录里的某个路径 **指向** 盘上的持久目录（**和 `data.link` 方向相反**，同一套联接实现）"。
但 `package-spec.md` 3.7 定义 `data.link` 是"**机器上的路径** 指向 **盘上的目录**（`target` ← `source`）"。两者都是"机器侧路径 → 盘上路径"，**方向相同**。
**后果**：照字面实现会给 `persist` 建反向联接（把盘上目录指向安装目录里的临时路径），卸载即丢数据；而 `persist` 恰恰是"用户数据不能丢"的那条路。
**建议**：删掉"方向相反"，改成"同一套联接原语，两侧角色不同：`data.link` 的机器侧是 Known Folder，`persist` 的机器侧是安装目录内的路径"。

### D13 参数表与细节不一致（`--source`/`--allow-scripts` 缺失、`--force` 双义）

- `commands.md` 4.2 `pd install` 的"主要参数"列：`--from-dir --as --dry-run --force`；5.1 细节却还有 `--allow-scripts`（`commands.md:190`）、`--source`。
- `--force` 在 5.1 里同时承担"装已撤回版本"和"覆盖冲突"两件事，而 `index-spec.md` 4.3 只描述了 yanked 用法、"覆盖冲突"的具体语义（覆盖谁？覆盖已装包？同名不同源？）无处定义。

**建议**：4.2 表补全参数；`--force` 拆成 `--force`（覆盖冲突）与 `--allow-yanked`（或反之），并在 `package-spec.md` §6 拒绝规则里指明"覆盖"对应哪一条。

### D14 `ext.json` 示例自身矛盾（声明 pages 却把 `ui` 权限关掉）

`spec.md:97`：示例 `pkgmgr` 声明了 `pages: [{ id: "packages", ... }]`，同一份示例的 `permissions` 里写着 `{ "kind": "ui", "allow": false }`；而 `window.md` 3.2 规定"扩展没声明 `{kind:"ui", allow:true}` 就调不了"。
**后果**：照抄示例的扩展页面能加载、一调命令就 `ERR_UNSUPPORTED`。
**建议**：示例改为 `allow: true`（有 pages 就必须有 ui 权限），并在 `spec.md` 2.7 加一句"声明 `pages` 而未开 `ui` 权限 → 加载时警告/拒绝"。

### D15 单实例锁：等待 / 拒绝 / 退出，三种说法

- `architecture.md:698`：拿不到锁 → "**等待或明确拒绝**"。
- `kernel.md` 4.1/4.2：拿不到 `Local\` Mutex 或心跳新鲜 → **退出**并返回 `ERR_BUSY`（客户端拿到 10）。没有"等待"分支。
**建议**：以 `kernel.md` 为准（退出 + 客户端排队/重试），删掉 architecture 的"等待"；并补上"客户端侧最多重试 N 次、间隔多久"。

## 2. 结构性缺口（P1：没有矛盾，但按现状写不出实现）

| # | 缺口 | 位置 | 影响 |
|---|---|---|---|
| G1 | **能力的可变性没有声明方式** | `spec.md:672` 说"`mutates` 的能力要排队"，但 `provides` 只是名字数组，没有任何字段能标"这个能力会写盘" | `call` 的串行化无法实现，两个 `storage.write` 可能并发 |
| G2 | **页面能调哪些命令没有授权规则** | `window.md` 3.2"权限 = 所属扩展的权限"，但"\`exec(['install'])\` 是调 pkgmgr 的命令" 这件事与页面所属扩展无关 | 任一 UI 扩展可执行全部业务命令，权限模型形同虚设 |
| G3 | **`ERR_*` 到退出码的映射不全** | `commands.md` 6.3 只覆盖 12 个码；`ERR_PROMPT_TIMEOUT`、`ERR_PROTOCOL`、`ERR_EXT_TIMEOUT`、`ERR_PKG_PLATFORM`、`ERR_HASH`、`ERR_IO`、`ERR_NET`、`ERR_INTERNAL` 无对应退出码 | 客户端只能硬编码猜测；`commands.md` §8 验收项 4 也查不到 |
| G4 | **`stickId` 无定义** | `spec.md:310`、`kernel.md:132`、`spec.md:409` | 管道发现、锁、多盘共存全靠它，却没说怎么算、存在哪、盘复制后是否要变 |
| G5 | **`requiresKernel` 的"内核 ABI 号"与协议号 `v`/`protocol` 的关系未定义** | `spec.md` 2.4、`spec.md:409` `protocolRange` | `>=1 <3` 到底比的是 `kernelVersion`（2.0.0）还是 ABI 整数？升级内核时会不会把所有扩展踢掉？ |
| G6 | **`adopt` 的版本号从哪来** | `architecture.md:733`、`commands.md:291` | store 目录名是 `<hash>-<id>-<ver>`，但 adopter 目录没有版本；`--id` 也没 `--version` |
| G7 | **`gc` 的"引用"定义自相矛盾** | `commands.md` 5.4：已装记录"永远算引用" | 记录指向的版本永远被引用 → 升级后的旧版本永远清不掉，与"旧版本保留直到 `pd gc`"`commands.md` 5.2）冲突 |
| G8 | **staging 清理策略两套** | `kernel.md` 2.1 `gc.stagingMaxAge: 24h` vs `kernel.md` 5.2 第 3 步"启动时删掉没有活跃任务的目录" | 刚取消的任务（未超 24h）会不会被启动恢复当垃圾删掉？ |

## 4. 总体架构报告

### 4.1 系统定位与不变式

一句话目标：**一块盘带着整套环境，插上一条命令把机器恢复成想要的样子；拔下来机器能恢复原样。**
可推导出四条硬不变式（文档里分散在 §1/§2/§9/§13，建议集中成一节）：

| 不变式 | 含义 | 文档中的落点 |
|---|---|---|
| I1 盘是唯一真身 | `store\` 内容不可变、路径即身份；机器侧一切都是可重建的"接线" | architecture §1、§6.1、§7 |
| I2 唯一写者 | 只有 `storage` 扩展碰盘/注册表；内核不碰盘、不认识"包" | architecture §3.1、§4.4、§18 |
| I3 先意图后提交 | 任何跨两次写的操作都要有 `begin/done` 边界，只认 `done` 为提交 | architecture §9.2、§11.2、kernel §5 |
| I4 失败不装一半 | 不支持的能力拒绝整包；半成品永远留在 staging | architecture §5.4、§13、package-spec §6 |

**这四条是全文最有价值的部分**，也是当前 15 处矛盾集中爆发的地方——越是"边界"，越需要把一句话写死（D1/D6/D7 全是边界处两个文档各说一套）。

### 4.2 分层与组件职责

```
             ┌───────────┐   ┌───────────┐
   用户 ────► │  pd.exe   │   │ window.exe│   壳：只解析连接/呈现开关，其余 argv 透传
             └─────┬─────┘   └─────┬─────┘   壳不写业务、不碰盘
                   └───────┬───────┘
                           ▼  命名管道 \\.\pipe\portabledev-<stickId>
                  ┌──────────────────────┐
                  │  pd-kernel.exe       │ 命令表 / 路由 / 扩展监督 / 管理命令 / 崩溃恢复
                  │  (控制面 only)        │ 不碰盘、不碰注册表、不碰网络
                  └───┬────┬────┬────┬───┘
        ┌─────────────┘    │    │    └──────────────┐
        ▼                  ▼    ▼                   ▼
   ┌─────────┐      ┌────────┐ ┌────────┐     ┌─────────┐
   │ storage │      │  log   │ │download│     │ pkgmgr  │
   │ 唯一写者 │      │        │ │ unpack │     │ 编排    │
   │ 租界/账本│      └────────┘ └────────┘     └────┬────┘
   └─────────┘                                      │ stdout/stdin 受限协议
                                               ┌────▼─────┐
                                               │ 包脚本    │ 无内核连接资格
                                               └──────────┘
```

| 层 | 职责 | 边界（不该做什么） |
|---|---|---|
| 壳 | 连接、渲染、交互、退出码透传 | 不做业务判断、不缓存命令表、不直接改盘 |
| 内核 | 路由、生命周期、串行化裁决、恢复 | 不碰业务数据、不决定租界、不理解包 |
| 内置扩展 | storage（唯一写者）/ log / download / unpack / pkgmgr（编排） | 互不直连，只按能力名经内核调用 |
| 包与包脚本 | 内容 + 声明 + 受限脚本 | 不带界面、连不上内核、副作用全走 storage |

这套划分的**最大优点是信任分级清晰**：壳与扩展可信、包脚本不可信且物理隔离（连管道资格都没有），因此省掉了大量"身份标签/能力令牌"的复杂度。**最大风险也在这里**：`pkgmgr` 成了唯一的信任转换点，它的白名单（`fetch/unpack/link/path.add/env.set/reg.set/reg.del/launch/assert/write/copy/move/rm`）实际上就是"第三方脚本能对机器做什么"的完整攻击面——但目前**没有任何一份文档定义白名单的粒度**（`path.add` 能不能加任意路径？`reg.set` 能不能写 HKLM？）。

### 4.3 三条主流程（时序）

**安装**（architecture §8，11 步）：
```
解析 → 预演(dry-run) → 下载(cache/blobs, 校 archive 哈希)
  → 租界(staging) → 解压 → 跑脚本(仍在 staging) → 文件断言
  → 算指纹 → 原子 rename 进 store → 接线(PATH/env/reg/launcher)
  → 激活断言 → 写记录+账本 done+存档点
```
关键时序决策（值得保留）：**脚本在 staging 里跑、store 收编后才接线**；断言分"文件断言（staging 前）"与"激活断言（接线后）"两类，这个切分是对的，避免了"PATH 还没生效就去跑 `--version`"的经典坑。

**升级**：新目录 + 挪 `current` 指针，PATH 不含版本号 → 零广播、零重开终端、回滚只挪指针。
**恢复**：intent 阶段机（`begin → renamed → done`）+ 账本 `begin/done` 配对 → 启动时按四种组合裁决。判定原则"只认 done"很干净，但前提是 D6/D7 必须先裁决，否则判定表会读错目录与文件。

### 4.4 状态与一致性模型

| 状态 | 载体 | 一致性手段 |
|---|---|---|
| 内容（不可变） | `store\<hash16>-<id>-<ver>` | 内容寻址 + 原子 rename（同卷） |
| 指针（可变） | `current\<id>` 联接 | 单次 rename，原子 |
| 接线（机器侧） | PATH / HKCU\Environment / 注册表 / 启动器 | 账本记录 before/after，可倒序还原 |
| 意图（在途） | `state\intent\*.json`（待裁决，见 D7） | 阶段机 + 启动扫描 |
| 快照（历史） | `state\generations\*.json` | 存**接线快照**而非从记录推导（这个判断正确：不同版本可能设不同 env） |
| 缓存 | `cache\blobs\<sha256>` | 内容寻址，可随时重建 |

**评分**：内容与指针层（Nix 式）很扎实；接线层靠账本补偿，模型正确但**粒度风险在"包级回滚 + 全局串行"**——批量安装时若第 3 个包失败，前两个已提交，用户看到的是"部分成功"，而文档只有"只回滚这个包"（`architecture.md` §11.1），没有"整批回滚"的可选项。建议补一个 `--transactional`（整批全成或全退），否则 `bundle install` 的语义会很尴尬。

### 4.5 安全模型

| 面 | 现状 | 评价 |
|---|---|---|
| 内容完整性 | 索引 `sha256` + 包内 `source.sha256` + 目录指纹，三层 | 好；但索引 `signature` 仍是预留 → **索引被改 = 可以指向任意包**，这是当前最实际的供应链缺口 |
| 解压安全 | `sanitize`（拒 `..\`/绝对路径/外链）+ `maxFiles/maxBytes` | 够用；建议补"符号链接/硬链接/稀疏文件"与 NTFS ADS、大小写冲突 |
| 权限 | 扩展声明 + 运行时租界；包脚本物理隔离 | 方向对，但白名单粒度未定义（见 4.2） |
| 凭据 | 全量 env 快照、不打码 | 与"日志不写 env"冲突（D10）；且 `ctx.env` 会随 `ext.invoke` 发给**每个**被调扩展 → 任一扩展都能拿到全部 token，这是比日志更严重的面 |
| 提权 | 一律普通权限，机器层合并成一次 UAC；子进程强制降权 | 设计正确（尤其"管理员启动的 Firefox 存不了书签"这条） |
| UI | WebView2 虚拟主机 + 严格 CSP + 无 Node 集成 | 好；缺"页面调命令的授权"（G2） |

### 4.6 部署与演进

- 部署单元：`app\`（只读基线 + `baseline.json`/`baseline\` 自愈）+ 盘根数据树；`app\` 拷走不可用（`kernel.md` §1.3）——这个判断诚实且重要。

- 兼容：格式带 `schema`、旧读新拒绝（但见 D9）。
