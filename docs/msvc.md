# Portable MSVC + Windows SDK

What is on the stick, why it is shaped like this, and what breaks if you touch it.

- MSVC toolset **14.44.35207** (`cl` 19.44.35229, x64, host x64)
- Windows SDK **10.0.22621.0**
- MSBuild **17.3.1** with the VC `v170` targets
- Location: `tools\msvc`, about **3.36 GB**

Installed with [msvc-kit](https://github.com/loonghao/msvc-kit) 0.2.23 (MIT):

```bat
msvc-kit download --vs-channel 2022 --msvc-version 14.44 --sdk-version 10.0.22621.0 ^
    --arch x64 --target <stick>\tools\msvc --parallel-downloads 16
```

msvc-kit pulls Microsoft's own payloads, verifies their SHA-256 and unpacks the MSIs
itself. Nothing is installed: no Visual Studio installer, no admin rights, no registry
writes, no `%ProgramFiles%` changes. 86 packages for the toolset, 258 for the SDK; the
receipts are kept in `tools\msvc\.msvc-kit\receipts\`.

The `msvc-kit.exe` that produced this tree (0.2.23, 7.4 MB, MIT) is kept next to those
receipts at `tools\msvc\.msvc-kit\msvc-kit.exe`, so the toolset can be updated from the
stick without downloading the tool again.

> **Licence.** msvc-kit is MIT, but the MSVC Build Tools and the Windows SDK it downloads
> are Microsoft's, covered by the
> [Visual Studio licence terms](https://visualstudio.microsoft.com/license-terms/). They
> may not be redistributed - a stick is fine for your own use, publishing the contents is

## Activation: three levels

| Level | How | What you get |
|---|---|---|
| Always on | `PortableDev apply` | `cl`/`link` on PATH, `INCLUDE`, `LIB`, `VCToolsInstallDir`, `WindowsSdkDir`, `WindowsSDKVersion` in the user environment |
| Per shell | `PortableDev shell --profile msvc` | the six extra variables Flutter's Windows build needs |
| Per script | `call scripts\msvc-activate.cmd` | the same six, in the current process |

The six live in `manifest\manifest.d\msvc.toml` as a `[[profile]]`, so there is one source
of truth; `msvc-activate.cmd` is for callers that are already a batch file (a `[[profile]]`
only reaches a shell that `PortableDev` started). They must not go into the registry:
`ProgramFiles(x86)` and `EnterpriseWDK` change how unrelated programs behave.

So plain C/C++ needs nothing:

```bat
cl hello.c
hello.exe
```

and Flutter needs one command first:

```bat
PortableDev.cmd shell --profile msvc
cd /d E:\项目\PiliPlus
flutter build windows --release
```

## Why the directory looks like a Visual Studio install

Flutter's Windows build is hard coded to a Visual Studio layout - not configurable, not
pluggable. It reads, in `tools\flutter\<ver>\packages\flutter_tools\lib\src\windows\`:

| Flutter/CMake expectation | Where it comes from in this tree |
|---|---|
| `%ProgramFiles(x86)%\Microsoft Visual Studio\Installer\vswhere.exe` (`visual_studio.dart:261`, "not user-controllable") | `pf86\...\vswhere.exe` - a ~40 line C program that prints one JSON instance; the variable is redirected to the stick instead |
| `<instance>\VC\Tools\MSVC\<ver>\bin\Hostx64\x64\cl.exe` (`:220`) | `VC\Tools\MSVC\14.44.35207\...` - the real toolset |
| `<instance>\VC\Auxiliary\Build\vcvars64.bat` (`:243`) | wrapper that calls `setup.cmd` |
| `<instance>\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\cmake.exe` (`:167`) | junction to `tools\cmake\4.4.5` |
| `<instance>\VC\Auxiliary\Build\Microsoft.VCToolsVersion.default.txt` (`cmVSSetupHelper.cxx`, `LoadVSInstanceVCToolsetVersion`) | one line: `14.44.35207`; **without this CMake reports "could not find any instance of Visual Studio"** |
| `CMake -G "Visual Studio 17 2022"` + `cmake --build` (`build_windows.dart:107`) | `MSBuild\Current\Bin\MSBuild.exe` + `MSBuild\Microsoft\VC\v170` |

The mechanism that makes CMake accept an instance the VS Installer has never seen is not a
hack: `cmVSSetupHelper.cxx` has an Enterprise-WDK branch that takes `VSINSTALLDIR` and
`VisualStudioVersion` from the environment when `EnterpriseWDK=True` and
`DisableRegistryUse=True`. `scripts\msvc-activate.cmd` sets exactly that.

## Directory map

```text
tools\msvc\
  setup.cmd                 generated by msvc-kit, %~dp0-relative, exports INCLUDE/LIB/PATH/SDK vars
  VC\Tools\MSVC\14.44.35207\ the toolset: bin\Hostx64\x64\cl.exe, include, lib
  VC\Auxiliary\Build\
    vcvars64.bat            -> call ..\..\..\setup.cmd
    vcvarsall.bat           -> same
    Microsoft.VCToolsVersion.default.txt   14.44.35207
  Windows Kits\10\          Include\Lib\bin for 10.0.22621.0
  MSBuild\                  MSBuild 17.3 + the C++ targets CMake's VS generator needs
  Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\   junction -> tools\cmake\4.4.5
  pf86\Microsoft Visual Studio\Installer\vswhere.exe     shim, compiled by this very toolset
  .msvc-kit\receipts\       msvc-kit provenance: versions, channels, payload hashes
```

Removed on purpose after the first build, so the tree stays readable: `Orca`, `MsiVal2`,
`Windows App Certification Kit`, `Reference Assemblies`, `Microsoft SDKs`
(`ExtensionSDKs`), 64 leftover `*.MSI` installer files and a handful of D3D/UCRT debug
DLLs - about 60 MB that only Visual Studio IDE tooling uses. Rebuilds after the removal
were verified (see below).

## Updating the toolset

```bat
msvc-kit download --vs-channel 2022 --msvc-version 14.44 --sdk-version 10.0.22621.0 ^
    --arch x64 --target E:\PortableDev\tools\msvc --no-sdk --parallel-downloads 16
```

After a version change, five places carry the number and all of them must agree:

1. `manifest\manifest.d\msvc.toml` - `version`, `[[path]]`, every `[[env]]`, and the
   `[[profile]]`'s `VisualStudioVersion`
2. `scripts\msvc-activate.cmd` - `VisualStudioVersion`
3. `tools\msvc\VC\Auxiliary\Build\Microsoft.VCToolsVersion.default.txt`
4. `tools\msvc\pf86\...\vswhere.exe` - the shim's `MSVC_INSTALL_VERSION`; rebuild it from
   `scripts\vswhere-shim.c` (the source sits next to the exe too, because `tools\` is not
   in git). The shim derives `installationPath` from its own location, so only the version
   string travels with a toolset upgrade.
5. `tools\msvc\setup.cmd` - regenerate rather than edit:
   `msvc-kit setup --script --shell cmd --portable-root "%~dp0" --dir E:\PortableDev\tools\msvc > setup.cmd`

Then `PortableDev apply --yes`, `PortableDev verify` (expect 30/30), and rebuild a Flutter
app once.

## Removing it

```bat
PortableDev clean --yes          # drops the PATH/env entries first
rmdir /s /q E:\PortableDev\tools\msvc
```

`tools\cmake` is shared - the junction inside `tools\msvc` points at it, so removing
`tools\msvc` does not touch CMake itself.

## Troubleshooting, from the actual failures

| Symptom | Cause | Fix |
|---|---|---|
| `could not find any instance of Visual Studio` | `Microsoft.VCToolsVersion.default.txt` missing (CMake reads the toolset version from it) | create it with the version string |
| same error, with `version=` given | CMake still asks `LoadVSInstanceVCToolsetVersion` first | same file |
| `LNK1181: cannot open kernel32.lib` | MSBuild looks the Windows SDK up in the registry | `UseEnv=true` so the C++ targets use `LIB` |
| `LNK1104: cannot open MSVCRTD.lib` | same, for the VC libs | `UseEnv=true` |
| `MSB8052: MSVC Toolset Version '14.44.x' is not compatible with 'v143'` | MSBuild 17.3 predates 14.4x | `CheckMSVCComponents=false` (same v143 ABI) |
| `flutter doctor` says `Unable to locate a Windows 10 SDK` | doctor queries `HKLM\SOFTWARE\Microsoft\Microsoft SDKs\Windows\v10.0`, which nothing wrote | cosmetic; builds do not read it |
| after deleting the whole `build\` directory: `file INSTALL cannot find .../build/native_assets/windows` | Flutter's generated install script expects that directory | delete only `build\windows`, or re-run `flutter build` (a fresh checkout is unaffected) |
