## 1. 这个工具是什么

一句话：

> **一块盘带着整套开发环境，插到任何电脑上，一条命令把电脑恢复成你要的样子；拔下来之后，电脑能恢复原样。**

它管三件事：

1. **内容**：工具本身（python、msvc、firefox……）放在盘的 `store\` 里。
2. **接线**：电脑上的 PATH、环境变量、注册表、启动器——这些是"派生状态"，随时可以重建。
3. **对应关系**：装了什么、装在哪、改过什么，都记在盘的 `state\` 里。

关键判断：**盘上的内容是"真身"，电脑上的东西是"接线"。接线坏了重接就行。**

---

## 2. 设计原则

后面的所有决定都服从这几条：

1. **可重建**：删掉盘上的接线和状态，一条命令能重建。
2. **不写死路径**：产物里不出现盘符，一律走稳定根或 `%~dp0`。
3. **少留机器状态**：能临时做的就不常驻，能不改注册表的就不改。
4. **一切副作用都要记账**：谁改的、改前是什么，都能查、能撤。
5. **用命令改状态，不用手写文件**：人能写的只有"包名列表"这种最简输入。
6. **尽量不改格式**：格式带版本号，新版能读旧版。

## 3. 总体架构（微内核）

```
        ┌──────────┐   ┌──────────┐
用户 ──►│ pd.exe   │   │ 窗口程序  │      ← 这两个是"壳"，不是扩展
        │(命令行的壳)│   │(窗口的壳) │
        └────┬─────┘   └────┬─────┘
             └──────────────┘
                            ▼  请求 / 事件流（argv 原样转发）
                 ┌─────────────────────┐
                 │  内核（常驻服务）      │
                 │  命令注册表 / 消息路由 │
                 │  扩展管理 / 管理命令   │
                 └──────┬──────────────┘
        ┌────────┬──────┴──────┬────────┐
        ▼        ▼             ▼        ▼
   ┌────────┐┌────────┐  ┌────────┐┌────────┐
   │ 存储   ││ 日志    │  │ 下载   ││ 包管理 │
   │(唯一写者)││        │  │ 解压   ││(编排)  │
   └────────┘└────────┘  └────────┘└────────┘
```

所有扩展都只和内核说话，扩展之间不直接连；`pkgmgr` 通过内核去找 `download`、
`unpack`、`storage`，自己不知道它们怎么实现。

包里的脚本由 `pkgmgr` 拉起，**不连内核**，只通过 stdout 向 `pkgmgr` 报告（见 4.10）。

### 3.1 内核做什么

只做三件事：

1. **传消息**：所有扩展之间、客户端和扩展之间的通信都经过内核。
2. **管扩展**：按需启动、监督、重启、停止。
3. **认几条管理命令**：不经过任何扩展，自己处理。

内核**不碰盘、不碰注册表、不碰网络**，也不理解"包"是什么。
内核碰盘的例外只有两处：读自己的配置和扩展目录（启动所需）、写一份兜底日志（日志扩展坏了时用）。业务数据一律走存储扩展。

> 租界不是内核发的，是存储扩展发的。内核只负责把申请和回复转过去。

### 3.2 内核的通信能力

微内核里，内核和任何扩展都是直连的：

- 客户端连上内核，内核按命令类型转给对应扩展；
- 内核可以主动问任何扩展"你还活着吗 / 现在什么状态"；
- 某个扩展坏了，内核可以直接重启它、或把它踢出列表。

所以不存在"应急通道"这种特殊设计——**它是内核本来就该会的事**。

### 3.3 内核管理命令

```
pd kernel ps              有哪些扩展在跑
pd kernel ext list        装了哪些扩展、版本、要求的 ABI
pd kernel restart <name>  重启某个扩展
pd kernel status          内核自身与存储扩展的连通状态
pd kernel log             内核自己的日志（不依赖日志扩展）
pd kernel stop [--force]  停止接新任务，等现有任务跑完再退出；--force 直接杀
```

这些由内核直接处理，不走 CLI 扩展。

`pd kernel stop` 的用途之一是**升级程序本身**：Windows 不允许覆盖正在运行的 exe，
所以换新版前先停内核，文件解锁后再覆盖。

### 3.4 控制面与数据面

内核**只走控制面**：

- 传的是：命令、状态、事件、**路径和句柄**；
- 不传的是：文件内容。

几百 MB 的安装包不会经过内核。下载扩展写进缓存区，解压扩展从缓存区读，
大家只交换路径。这样内核不会被 I/O 拖死，也不会变成内存瓶颈。

### 3.5 客户端上下文

内核是常驻的，它的环境和你敲命令时的环境不一样（代理、PATH、当前目录都可能不同）。
所以**每次请求都带一份上下文快照**：

| 带上什么 | 为什么 |
|---|---|
| 当前目录 | 相对路径要按用户所在位置解析，不是按内核的工作目录 |
| 环境变量 | 代理、`HTTP_PROXY` 之类只在你终端里有 |
| 终端宽度 / 是否支持颜色 | 输出格式由客户端决定，内核不猜 |

内核**不读自己的环境**做业务判断。

### 3.6 协议版本

客户端连上内核先握手，报自己的协议版本：

- 不兼容 → 内核明确拒绝，并提示“内核版本过旧，请停止后升级”；
- 扩展的版本要求由 `ext.json` 的 `requiresKernel` 管，和客户端握手是两条线。

### 3.7 壳（客户端）不是扩展

准确的说法是：**功能皆扩展，客户端是壳。**

| 壳 | 干什么 | 不干什么 |
|---|---|---|
| `pd.exe` | 连内核 → **原样转发 argv** → 渲染事件 → 透传退出码 | 不写业务逻辑，不解析命令，不直接碰盘 |
| `窗口程序` | 同一套事件流，渲染成窗口 | 同上 |

壳只有两个，它们**不是扩展**，也不需要是。好处：

- 没有多余的进程，没有 stdio 跨进程转发；
- `Ctrl+C`、管道、`--json` 都是天然工作；
- 命令行和窗口行为一致（同一套事件、同一套权限），不会出现两套实现。

**保底通道**：`pd --raw '<json>'` 直接发原始请求，不经过任何解析。
万一命令查询取不到，还能手动救。

### 3.8 命令表只在核心里

命令是**静态声明**的（写在每个扩展的 `ext.json` 里），但**不发给客户端**。

- `pd` 只解析连接/呈现类开关（`--root`、`--json`、`--no-color`、`--quiet`、`--trace`），其余 argv 原样转发；内核解析：认就路由给对应扩展，不认就返回错误；
- 这张表只存在于内核内部，客户端不缓存、不校验、不比对哈希。

好处：客户端不会过期，也没有"schema 失配"这类分支。

**帮助和补全按需问**：

```
pd help              内核返回命令列表（名字 + 一句话）
pd help install      内核返回这个命令的参数说明和示例
pd complete ins      内核返回以 ins 开头的候选（给 shell 补全）
```

只有真敲 `--help` 或按 Tab 时才发生，平时执行命令完全不碰。

代价：`pd` 不能本地校验参数（打错由内核报错，并带"你是不是想敲 install"），
界面要画表单得先调一次 `pd help --json`。

规则：

1. **内核自己的管理命令也在这张表里**（`kernel ps` / `kernel stop` / `kernel ext list`），
   走同一条路，`pd` 没有特殊分支。
2. **冲突检测**：两个扩展注册同名命令 → 后加载的整个不加载，并说明冲突；
   不做静默覆盖。
3. **按需拉起**：敲了某个命令，但提供它的扩展没在跑 → 内核拉起来再转发
   （先按 `depends` 拉起依赖）。
4. **拉起失败**（文件没了 / 依赖缺 / ABI 不符 / 超时）→ 明确报错：
   哪个扩展、为什么、怎么修；不重试、不猜。
5. **空闲退出**：默认常驻（\`kernel.idleExit = 0\`）；配了时长才按"最近使用 + 没有在途请求"计时退出。

### 3.9 进程模型（内核 / 扩展 / 壳 的分工）

进程管理不属于内核。内核只做**自举必须**的那件事——拉起并监督扩展；其余进程交给 `proc` 扩展，
人类可读文本和确认交互交给壳。完整规范见 [proc.md](proc.md)。

| 谁 | 负责 | 不负责 |
|---|---|---|
| 内核 | 扩展的启动/监督/重启；`pd kernel ps` 等内核自己的管理命令 | 业务进程、stdio、进程文案 |
| `proc` 扩展 | Job Object、限额、超时、整树终止、stdio 代理、脱离、系统级枚举/结束 | 脚本策略、机器接线、文案 |
| `pkgmgr` | 包脚本策略（白名单、请求协议） | 进程机制 |
| 壳（`pd.exe`） | `pd run`/`pd shell` 的进程拉起（stdio 原生）、所有文本与确认 | 业务规则 |
| `storage` | 机器接线与接线提权的账本 | 进程 |

三条硬规则：

1. **进程树用 Job Object 表示**：杀树 = `TerminateJobObject`，不靠枚举子进程；
   创建即入 job（`CREATE_SUSPENDED` → assign → resume），不留竞态窗口。
2. **脱离只能发生在出生时**（`CREATE_BREAKAWAY_FROM_JOB` + job 允许 `BREAKAWAY_OK`）；
   脱离后的进程不属于受管树，只记日志。
3. **提权只做一次性**：每次操作一次 UAC、用一次性提权实例完成；不做常驻提权进程。

进程按三档等级（`0` 普通 / `1` 需要管理员 / `2` 关键），机制层只回数字，
文案由壳按等级生成。

**视图不合并**：扩展进程归 `pd kernel ps`（内核的孩子），业务进程归 `pd proc`（`proc` 扩展的孩子），
谁的孩子谁管；内核不当扩展能力调用方，统一展示留给壳 / 窗口层。
唯一例外是 `pd run`：内核只产出启动规格、由壳执行（stdio 必须属于终端），内核不拉起业务进程。

## 4. 扩展

### 4.1 扩展是什么

扩展 = **给程序加功能的独立进程**。

- 可以有界面（网页），也可以没有；
- 可以是 `.exe`、`.ps1`、`.py`，按声明选解释器——**核心扩展也允许用脚本**，
  先保证能跑起来，效率问题以后再说（脚本冷启动比 exe 慢几百毫秒，能接受）；
- 全部**按需启动**，用完退出（性能开销可接受，不为它破例）。

### 4.2 扩展怎么声明

每个扩展一个目录，里面一份 `ext.json`：

```
extensions\
  storage\
    ext.json
    storage.exe
  pkgmgr\
    ext.json
    pkgmgr.exe
```

字段清单见 [spec.md](spec.md) 第 2 节（`name`、`entry`、`interpreter`、`requiresKernel`、
`depends`、`permissions`、`provides`、`commands`、`pages` 等）。

### 4.3 扩展的权限

- **声明但不审批**：权限写在 `ext.json` 里，装的时候不弹窗（都是自己写的），
  但 `pd kernel ext list` 能看到每个扩展要了什么。
- **运行时仍要申请**：声明只是"我大概需要"，每次真正动手还要向存储扩展要租界。

### 4.4 租界（grant）

扩展不直接拿到"任意写盘"的能力，而是每次操作向**存储扩展**申请：

```
申请：{ "want": "workdir", "hint": "unpack-firefox" }
存储：建一个受控的临时目录，记一笔账，返回路径
扩展：在这个目录里自由读写（批量操作不走消息）
结束：扩展报告成功/失败
存储：成功 → 校验目录指纹 → 原子挪进 store\<哈希>-<id>-<ver>
      失败 → 整个目录删掉
内核：全程只转发消息，不参与数据路径，也不知道 store 在哪
```

记账粒度是**目录**，不是单个文件。这是为了性能：解压几万个文件不可能每个都走一次消息。

租界的意义是：**扩展在哪个范围内动手，存储扩展是知道的**。出了这个范围，存储扩展不认。

### 4.5 版本兼容

- `ext.json` 写 `requiresKernel`；
- 内核启动时检查，**不匹配就跳过这个扩展**，并在 `pd kernel ext list` 里标红说明原因；
- 不做"尽量兼容"，避免半死不活的状态。

### 4.6 内置扩展（随程序发布）

| 扩展 | 职责 | 是否必须 |
|---|---|---|
| `storage` | 唯一直接碰盘和注册表的；发租界、收编、写审计、执行撤销原语 | 必须 |
| `rollback` | 读审计流、编排撤销、出计划与报告；执行都交给 storage（见 9.2 / 11.1） | 必须 |
| `log` | 结构化日志：收、存、查、真空；实现可替换（契约见 spec 5.3.1），内核只留兜底 | 必须 |
| `download` | 按 URL 下载、校验哈希、写缓存 | 必须 |
| `unpack` | 解压 zip / tar.gz / 7z / msi | 必须 |
| `pkgmgr` | **流程编排**：下载 → 解压 → 收编 → 接线（见 4.9） | 必须 |
| `ui` | 提供页面（窗口壳加载它，见 4.11） | 可选 |
| `scoop-src` | 读 Scoop 清单并转成内部格式 | 可选 |

> "必须"的意思是：不装就干不了正事；内核本身仍能启动并报告缺了谁。
>
> **没有 `cli` 扩展**：命令行本身就是壳（`pd.exe`），不是扩展，见 3.7。

### 4.7 信任分级

| 谁 | 等级 | 能做什么 |
|---|---|---|
| 扩展（`extensions\` 里的） | **可信** | 业务命令、调存储扩展、申请租界 |
| 用户客户端（`pd.exe`、窗口） | **可信** | 业务命令 + 管理命令 |
| 包里的脚本 | **受限** | 只能调业务命令；**不能**连内核、不能读写状态、不能提权 |

理由：包可能来自 Scoop 源或别人给的 `.pdpkg`，脚本是第三方代码。
扩展和壳是你自己写的，属于另一个信任层。

包脚本的受限做得更彻底：**它根本不连内核**，只跟拉起它的 `pkgmgr` 说话（见 4.10）。
连不上内核，就不存在"用身份标签挡一下"的复杂度。

### 4.8 生命周期、取消与租约回收

**启动**：`pd` 发现内核没在跑 → 拉起 → 之后常驻。

**停止**：`pd kernel stop` 停止接新任务，等现有任务结束再退出；`--force` 直接杀。

**取消**：客户端按 `Ctrl+C` → 告诉内核 → 内核转给正在干活的扩展 → 扩展停手。

**卡死**：扩展超时没响应 → 内核熔断，杀掉它的进程树。

**租约过期**：每个租界带有效期；内核启动时扫一遍，过期租界的临时目录直接删。

**半成品**：永远待在租界里，永远进不了 `store`。所以“取消”最坏只是浪费一点磁盘，
不会留下一个看起来装好了、其实残缺的包。

### 4.9 流程编排

一条安装流程由 **`pkgmgr` 扩展**编排，内核不知道流程：

```
pkgmgr: 问 download 要内容（拿回缓存路径）
pkgmgr: 问 storage 要租界（拿回临时目录）
pkgmgr: 让 unpack 在租界里解压
pkgmgr: 校验目录指纹 → 告诉 storage 收编
pkgmgr: 让 storage 建 current 指针、改 PATH/注册表、生成启动器
pkgmgr: 跑包脚本（受限身份）
pkgmgr: 跑断言
pkgmgr: 成功 → 让 storage 存一个存档点
```

每个扩展只干自己那件事，不知道全局。改流程只动 `pkgmgr`。

### 4.10 包脚本：只跟 `pkgmgr` 说话

包脚本可能来自 Scoop 源或别人给的 `.pdpkg`，按第三方代码对待：

```
pkgmgr: 用 Job Object 拉起 install.ps1（工作目录=staging 内的包目录，注入 PD_* 环境变量）
脚本:   往 stdout 打印结构化行（log / progress / request）
pkgmgr: 读这些行，转成标准事件；遇到 request 就代它去调业务命令，结果写回脚本 stdin
pkgmgr: 脚本退出后检查退出码，非 0 就按失败处理
```

约束：

- **脚本连不上内核**，它连 Named Pipe 的资格都没有；
- 脚本能做的事，只能是 `pkgmgr` 愿意代它做的事（白名单）；
- 脚本进程挂进 Job Object，超时或取消时整棵树一起杀；
- 脚本的所有副作用仍然由 `storage` 执行和记账；
- **脚本在 staging 里跑，收编进 store 之前**（否则等于改不可变区）。

请求/回执的完整格式见 8.2 与 [package-spec.md](package-spec.md) 3.5。

### 4.11 页面扩展与窗口壳

- 页面扩展（`ui`）提供网页文件，声明"我提供哪些页面"；
- 窗口壳（`window.exe`）加载这些页面，并通过宿主桥转发它们的请求到内核；
- 页面能读数据、能调业务命令，权限和扩展同级（都是你自己写的）。

窗口壳和 `pd.exe` 是**平级的两个壳**：同一套事件流、同一套权限、同一个内核。

## 5. 包

### 5.1 包和扩展是两回事

| | 包 | 扩展 |
|---|---|---|
| 是什么 | 要装进 `store\` 的工具 | 程序自己的功能部件 |
| 放哪 | `store\<哈希>-<id>-<version>\` | `extensions\<name>\` |
| 谁写 | 你、我、`pd adopt` | 你、我 |
| 能带界面吗 | **不能** | 能（网页） |

**界面的归属只有一个：扩展。包永远不带界面。**

### 5.2 包文件格式

一个包 = 一个压缩包（`.pdpkg`，本质是 zip）：

```
mytool-1.2.0.pdpkg
  package.json        说明书（必须有）
  files\...           内容（可选：也可以只写下载链接）
  install.ps1         安装脚本（可选）
```

规则：

- `package.json` 是**唯一必需的**；
- 内容是本地文件，或写成下载链接 + 哈希，两种都行；
- 脚本可选，`package.json` 里声明要不要跑、跑哪个。

### 5.3 package.json 的职责

写清楚：名字版本、从哪来、怎么解、怎么接（PATH/环境变量/注册表/启动器）、
怎么验（断言）、要不要跑脚本、数据放哪。

**字段清单见 [package-spec.md](package-spec.md) 第 3 节**，这里不重复。

### 5.4 两条来源

1. **包文件**：`pd install .\mytool-1.2.0.pdpkg`、`pd install https://.../x.pdpkg`
2. **Scoop 式源**：`pd install fd` —— 从索引找到清单，**先转换成我们的格式**，再走同一条流程。

转换的规则：

- 能映射的字段直接映射（版本、URL、哈希、解压方式、依赖）；
- 遇到我们不支持的能力（安装器脚本、快捷方式、写系统环境变量等）→ **整个包拒绝**，并说明是哪一条不支持；
- 绝不"装一半"。

### 5.5 离线时能不能装

逐包判断，不看全局开关：

| 包的情况 | 离线能不能装 |
|---|---|
| `files\` 里自带内容 | 能 |
| 需要下载，但 `cache\blobs\` 里已有该哈希 | 能 |
| 需要下载，缓存里没有 | 不能，报错并给出 `pd fetch <包>` 预取命令 |

`--offline` 只禁联网，不禁用盘上已有的内容。细节见 [index-spec.md](index-spec.md) 7.1。

## 6. 存储布局

```
v2\
  app\                                   程序（内核、pd.exe、窗口程序）
  store\
    <16位哈希>-python-3.13.18\            内容，装好永不改
  current\
    python                                目录联接 -> store 里的某个版本
  home\
    <包名>                                用户持久数据；C:\Dev\home\<包名> 指向这里
  staging\
    <任务号>\                             解压/脚本干活的租界（同卷，收编后清空）
  cache\
    blobs\<sha256>                        下载缓存，按内容指纹
  packages\
    *.pdpkg                               你的包文件
  extensions\
    <name>\ext.json                       扩展
  state\
    records\<id>.json                     包记录
    ledger\<yyyy-mm>.jsonl                账本（可撤销的改动）
    intent\<任务号>.json                  未完成的意图（崩溃恢复用）
    logs\<...>.jsonl                      日志
    generations\<序号>-<时间>.json         存档点
    sources\<源名>\index.json             索引缓存
    machine\<机器标识>\...                 跟机器绑的东西
    lock                                  单实例锁
  config\
    settings.json                         全局配置
    sources.json                          源配置
```

> **盘要求 NTFS**（见 kernel.md 1.0）：`current\`、`home\`、`app\current\` 都是目录联接，
> 且 `staging\` 收编进 `store\` 依赖同卷 `rename`。exFAT / FAT32 不支持，不做降级。
>
> 配置统一放在 `config\` 目录下：`settings.json` 管稳定根、存档点数、缓存上限这些，
> `sources.json` 管源（见 [index-spec.md](index-spec.md)）。不再有根目录的 `config.json`。

### 6.1 为什么路径里带哈希

借用 Nix 的思路：**路径就是身份**。

- 内容一样，路径就一样，不会存两份；
- 内容一变，路径就变，不会出现"同一个版本号、其实内容不同"；
- 升级 = 新目录 + 挪指针，旧目录原样保留。

**路径里只放 16 位十六进制**（完整哈希的前 16 个字符），完整哈希存在记录里。

原因：Windows 的 260 字符限制是真实存在的，`node_modules`、MSVC 的深目录一叠加就爆；
而且不少老工具不认 `\\?\` 长路径写法，会直接崩。16 位（64 bit）对几千个包的量级，
碰撞概率可以忽略；真撞了就在后面加 `-2` 后缀并在日志里记一笔。

代价：人眼可读性差 —— 所以对外展示和 PATH 都走 `current\` 指针。

**store 路径用哪个哈希**：

| 包的类型 | 用什么 |
|---|---|
| 有 `source.sha256`（下载压缩包） | 压缩包哈希 |
| 只有 `files\`（自带内容） | `.pdpkg` 文件本身的哈希 |
| 包目录（开发模式，无 `.pdpkg`） | 解压后的目录指纹 |

三种都是"内容决定路径"，只是内容的载体不同。

### 6.2 两份哈希

| 哈希 | 算什么 | 干什么 |
|---|---|---|
| 压缩包哈希 | 下载到的那个文件 | 决定 store 路径；和说明书里的值比对 |
| 目录指纹 | 解压后的整个目录 | 存进记录，用来发现"装完之后被改过" |

两份都**存进记录**。

### 6.3 缓存

- 按 `sha256` 存，一个文件只有一份；
- 从哪个源来、叫什么名字，都不影响存哪；
- 离线安装、换源、复制给别人，都靠它。

## 7. 激活（接线）

装完不等于能用，还要"接上"：

| 接线 | 做法 |
|---|---|
| PATH | 写 `C:\Dev\current\<id>\...`，一个包一条，**不含版本号** |
| 环境变量 | 写 `HKCU\Environment`，值里用稳定根，不写盘符 |
| 注册表 | 按包声明的键写，先备份原值 |
| 启动器 | 生成 `.cmd`，一律用 `%~dp0` 或稳定根，指向 `current\` |
| 家目录 | `C:\Dev\home\<包名>` 联接 → `{{STICK}}\home\<包名>`；`{{HOME}}` 就是这个稳定根路径 |
| 撤销 | 每条接线改动在审计流里带 `undo`（原值 + 逆操作），`pd clean` 与 `rollback` 共用 |

因为 PATH 不含版本号：

- 升级只挪 `current\` 指针，**PATH 不变、不用广播、不用重开终端**；
- 回滚就是指针指回去，几秒。

## 8. 安装一个包的完整流程

由 `pkgmgr` 扩展编排，各扩展各干一段。
**脚本必须在 staging 里跑完，store 才收编**——因为 store 是不可变的，脚本会改文件。

```
1. 解析     pkgmgr 找到说明书（包文件 / 源 / 本地目录）
2. 预演     pkgmgr 列出要做的事，什么都不改（--dry-run 到这里停）
3. 取内容   download 下载到 cache\blobs，校验压缩包哈希
4. 解压     unpack 在 storage 给的租界（staging）里解压
5. 跑脚本   如果声明了 install.ps1，在 staging 里跑（改的是 staging，不是 store）
6. 文件断言 存在性 / JSON 字段 / 文件哈希 —— 全部对着 staging 检查
7. 算指纹   storage 对 staging 目录算哈希 → 写进记录（用来发现装完被改过）；
           只有"包目录（开发模式，无 .pdpkg）"才用这个指纹决定 store 路径，
           其余两种在解压前就由 archive / .pdpkg 哈希定好了（见 6.1）
8. 收编     原子 rename：staging → store\<哈希>-<id>-<ver>（同卷）
9. 接线     storage 建 current 指针、改 PATH/环境变量/注册表、生成启动器
10. 激活断言 命令类断言（firefox --version）：此时 PATH 已生效
11. 提交    写记录 + 账本 intent 完成 + 存一个存档点
```

失败时按账本回滚：接线部分逐条还原，store 目录按 intent 删掉，记录不写。

### 8.1 两类断言

断言分两种，执行时机不同，混在一起实现必卡壳：

| 类型 | 例子 | 什么时候跑 | 对谁 |
|---|---|---|---|
| **文件断言** | `exists`、`json`、`fileHash`、`missing` | 收编**之前** | staging 目录 |
| **激活断言** | `command`（`firefox --version`） | 接线**之后** | 机器环境 |

`package.json` 里可以显式写 `phase`：`staging` / `active`；
不写时按类型推断（`command` → active，其余 → staging）。

### 8.2 脚本能做什么

脚本**不能直接调 `pd`，也连不上内核**。它往 stdout 打印请求，由 `pkgmgr` 代它执行；
每发一个请求，就**从 stdin 读一行回执**。

```json
// 脚本 → stdout（必须有 id）
{"type":"request","id":"1","cmd":"fetch","args":{"url":"...","sha256":"..."}}
// pkgmgr → 脚本 stdin
{"id":"1","ok":true,"data":{"path":"...\\cache\\blobs\\ab12..."}}

{"type":"request","id":"2","cmd":"link","args":{"target":"...","source":"..."}}
{"id":"2","ok":false,"error":{"code":"ERR_IO","message":"目标已存在"}}
```

要点：

- **请求必须带 `id`**，回执按 `id` 对应；没有回执的请求视为失败；
- 命令名是**裸名**（`fetch` / `unpack` / `link` / `path.add` / `env.set` /
  `reg.set` / `reg.del` / `launch` / `assert` / `write` / `copy` / `move` / `rm`），
  **不带 `pd` 前缀**——脚本根本不认识 `pd`；
- 脚本按需读取回执；pkgmgr 写回执带超时（默认 30s），脚本不读就判失败；
- 不在白名单里的命令 → 回执 `ok:false` + `ERR_UNSUPPORTED`，脚本应停止；
- 其他输出（普通打印、进度行）可以出现在 stdout，但要带 `type` 字段，
  没有 `type` 行按日志处理。

完整字段见 [package-spec.md](package-spec.md) 3.5。

原因：脚本直接动手的部分账本看不见，`clean` 就还原不干净。

## 9. 数据

| 数据 | 位置 | 谁写 | 用途 |
|---|---|---|---|
| 包记录 | `state\records\<id>.json` | 程序 | 装了什么、装在哪、两份哈希 |
| 账本 | 日志提供者的审计流（`log.audit`） | 存储扩展（写）、回滚扩展（读/记进度） | 可撤销的改动 + 改前的值 + `undo` |
| 日志 | `state\logs\*.jsonl` | 日志扩展 | 全部输出，按字段筛 |
| 存档点 | `state\generations\*.json` | 程序 | 某个时刻激活了哪些版本 |

### 9.1 记录

一个包一份，人能直接看、能手工改（改完要 `pd doctor` 校验）。

### 9.2 账本（审计流）

账本不再由存储扩展单独写文件，而是作为**审计流**存放在日志提供者里（spec 5.3.2）：

- **写**：存储扩展在改状态前先写审计条目，等 `call.ok`（已 fsync）才继续；
  写不进去就中止，不允许"改了但没记上"；
- **条目自带 `undo`**：写入方给出 `{cap, op, args}`，回滚时照做——读取方不需要认识业务语义；
- **按任务分组**：`task` 号同时关联 store/记录（11.2 的 intent）和接线改动；
- **事务边界**：`begin` / `done` 成对，只有 `done` 算"这批改动已提交"；
- **保留**：`log.auditRetentionDays`（默认 7 天）；过期后回滚拒绝执行，不半撤。

```jsonl
{"ts":"...","task":"t42","phase":"begin","op":"install","pkg":"firefox"}
{"ts":"...","task":"t42","op":"path.add","before":[],"after":["C:\\Dev\\current\\firefox"],
 "undo":{"cap":"storage.wire","op":"path.set","args":{"scope":"user","value":[]}}}
{"ts":"...","task":"t42","op":"registry.set","key":"HKCU\\...",
 "before":{"kind":"REG_SZ","value":"x"},"after":{...},
 "undo":{"cap":"storage.wire","op":"registry.set","args":{...}}}
{"ts":"...","task":"t42","phase":"done"}
```

回滚由 `rollback` 扩展负责编排（见 11.1）：它只做三件事——按 `task` 查询、倒序执行 `undo`、
把自己的进度写回审计流。真正动盘、动注册表的仍然只有存储扩展。

这批边界同时覆盖 store/记录（11.2 的 intent）和接线（PATH/环境变量/注册表/启动器），
两者用同一个 `task` 号关联。

### 9.3 日志

- 结构化文本（一行一条 JSON），**不是二进制**；
- 能按包、级别、时间、操作筛：`pd log --pkg firefox --level error --since 1h`；
- 日志扩展是扩展，内核自己留一个最小出口（写固定文件），防止"日志扩展坏了就什么都不知道"。

### 9.4 存档点

- 每次成功改动存一档；
- 默认保留数量**可配置**；
- `pd rollback` 回到某一档，`pd gc` 删除没有被任何档引用的版本和缓存。

**存档点存的是"那一刻的接线快照"，不只是版本列表**：

```json
{
  "schema": 1,
  "seq": 15,
  "at": "2026-11-23T20:05:00+08:00",
  "packages": { "python": "3.13.18", "node": "22.11.0", "msvc": "14.44" },
  "path": ["C:\\Dev\\current\\python\\Scripts", "C:\\Dev\\current\\python", "..."],
  "env": { "NODE_OPTIONS": "-max-old-space-size=4096", "PUB_CACHE": "Z:\\...\\cache\\pub" },
  "registry": [ { "hive": "HKCU", "key": "Software\\Classes\\.md",
                  "name": "", "type": "REG_SZ", "value": "MyMarkdown" } ],
  "launchers": [ { "name": "Firefox", "path": "Z:\\PortableDev\\Firefox.cmd",
                   "sha256": "..." } ]
}
```

为什么存快照而不是从记录推导：**不同版本的包可能设不同的环境变量**。
`node 22` 设 `NODE_OPTIONS=A`、`node 23` 改成 `B`，回滚到 22 时，
如果只按记录推导，`A` 已经没地方找了。快照 JSON 只有几 KB，存下来最省心。

**存档点不复制内容，只复制引用。** `store\` 不可变、路径即身份（6.1），
所以一代快照就是几 KB 的引用集合（包→版本、PATH、环境变量、注册表、启动器）：

- 保留 N 代**不额外占空间**——旧版本目录本来就要留到 `pd gc`；
- 升级 = 新目录 + 挪指针，旧目录就是"上一代的内容"，天然已经在盘上；
- 真正的成本只在"升级后旧版本还没 gc"的那段时间，由 `gc.keepGenerations` 控制；
- `app\` 自身升级同理：版本目录 + `app\current` 联接，切换零复制。

一句话：**不可变 + 内容寻址，把"快照"从拷数据变成了记指针。** 只有冷备份（拷到别的盘）
才真的需要复制字节。

`env` 里只存**托管变量**（包声明的），不存用户自己的环境变量。

## 10. 权限与提权

### 10.1 模型

- 内核、存储扩展、其它扩展，平时都以**普通权限**运行；
- 只有真正要动"机器层"时才提权：
  - 建/删稳定根（`C:\Dev`）；
  - 写 `HKLM`；
  - 改完整性标签。
- 一次操作**最多一次 UAC**：把这些改动攒成一个批次，提权执行一次。

### 10.2 不考虑"没有管理员"的场景

- 提权被取消 → 报错退出，不改任何东西；
- 不设计降级模式（没有 `--no-junction` 这种东西）。

### 10.3 子进程必须降权

`pd run`、`pd shell`、生成的启动器，**无论父进程是不是管理员，启动的用户程序都必须回到普通令牌**。否则会出现"管理员启动的 Firefox 存不了书签"这类问题。

## 11. 失败与恢复

### 11.1 单个包失败

- 只回滚这个包自己的改动；
- 其它包继续；
- 最后汇总报告哪些失败。

回滚不自己实现：`pkgmgr` 失败时调用 `rollback` 扩展（`rollback.run {task}`），
由它读审计流、倒序执行条目里的 `undo`，并把进度写回审计流（崩溃可续）。
存储扩展只提供原语，不认识"任务"与"批次"。

### 11.2 崩溃与 intent 日志

"把目录挪进 store" 和 "写记录" 是**两次写**，中间崩溃就会不一致。所以每一步都要留意图：

```
1. 写 intent 文件 state\intent\<task>.json {task, pkg, target=<store路径>, phase=begin}
2. staging 解压 / 跑脚本 / 算指纹
3. 原子 rename：staging → target
4. 原地更新 intent 文件 {phase=renamed}
5. 写包记录
6. 原地更新 intent 文件 {phase=done}（这一条成功才算提交；账本条目与它共用 task 号）
```

启动时扫未完成的 intent，按三种情况恢复：

| 目录在 store | 记录存在 | 处理 |
|---|---|---|
| 有 | 无 | 补写记录（默认；`pd recover --drop` 则删目录） |
| 无 | 有 | 删记录（内容没了，记录是假的） |
| 无 | 无 | 当失败清理，删 intent |
| 有 | 有 | 正常提交，删 intent |

原则：**只认 intent 的 `done` 为提交**。没有 `done` 的一律算"没装上"，
宁可让用户重装一次，也不留一个半真半假的状态。

内核启动时自动跑一遍；也可以手动 `pd recover [--adopt|--drop]`（见 [commands.md](commands.md) 5.14）。

### 11.3 单实例锁

- 盘根一把锁，记录 PID、机器、时间；
- 同一块盘同时只有一个内核在写；
- 拿不到锁 → **明确拒绝**（`ERR_BUSY`），不等待、不抢占；客户端可自行重试（细节见 kernel.md 第 4 节）。

## 12. 兼容

- 记录、`package.json`、`ext.json`、`config\settings.json`、`config\sources.json`、`index.json` 都带格式版本；
- 新版能读旧版并自动升级；
- **状态文件**（记录 / 索引缓存 / 配置）旧版读到新版 → **直接拒绝**并提示升级，不猜；
- **声明文件**（`ext.json` / `package.json`）不受此限：按 `requiresKernel` / `minKernel` 判定，未知字段按 spec.md 2.11 忽略——声明了更新的 `schema` 但 ABI 满足时，仍然尝试加载；
- **尽量不改格式**：改之前先想有没有兼容的办法。

## 13. 安全

| 风险 | 做法 |
|---|---|
| 内容被换 | 说明书里必须有哈希，下载后必须对上 |
| 压缩包路径穿越（zip slip） | 拒绝 `..\`、绝对路径、指向盘外的链接 |
| 解压炸弹 | 声明大小 + 解压上限 + 文件数上限 |
| 不支持的安装器 | 整个包拒绝，不装一半 |
| 扩展乱来 | 声明权限 + 运行时申请租界；账本可查 |

## 14. 接管旧盘

1. `pd adopt` 扫盘上现有的 `tools\`，生成包记录；
2. 旧 `manifest.d\*.toml` **留着，但不再读**（纯参考）；
3. 接管稳定根和 PATH；
4. 旧程序保留，随时能换回去；
5. 验收：`pd selftest` 通过。

`adopt` 默认按**移动 + 可回退**处理：

1. 算目录指纹 → 决定 store 路径；
2. `rename` 旧目录 → `store\...`（同卷，秒级）；
3. 生成记录、建 `current` 联接、跑断言；
4. 验证通过后才允许 `pd gc` 清掉旧的空目录；失败则 `rename` 移回去并删记录。

不改用复制，因为几 GB 会翻倍；也不直接删旧目录，因为失败要能退。

### 14.1 环境清单 `env.bundle`

为了"换一块盘 / 换一台机器 / 备份"三个场景，增加一个纯文本清单：

```
# env.bundle
source core
python@3.13.18
node@22.11.0
local/mytool@0.1.0
```

- `pd bundle export` 生成，`pd bundle install` 消费；
- 它是**意图**，不是状态：不记哈希、不记路径，只记"要哪些包、什么版本"；
- 真正的状态（记录、存档点）仍在 `state\` 里；
- 换机器时：拷盘 → `pd adopt`（如果用旧盘）或 `pd bundle install`（如果新装）。

## 15. 验收

不是"单元测试全绿"，而是端到端：

> 干净机器（或清空状态的虚拟机）上：
> 接管旧盘 → 装一个包 → 升级 → 回滚 → 故意拔电 → 重启后状态自洽。

再加两级自检：

- `pd selftest`：快查，各包 `--version` 比对；

## 16. 已经付出代价的地方（心里有数）

| 选择 | 代价 |
|---|---|
| 微内核 | 简单命令 3 个进程，安装 6–7 个；调试要看多处日志（可以把 download+unpack 合成一个 `fetch` 减轻） |
| 全部扩展按需启动 | 每条命令多几十毫秒 |
| 纯哈希路径 | 路径长、可读性差，排查要查记录 |
| 两份哈希 | 安装时多扫一遍目录 |
| 每包独立回滚 | 账本要能按包切分，不能只整体回滚 |
| 接 Scoop 源 | 字段映射要跟着上游变 |
| 窗口只是容器 | 不装界面扩展时就是白窗 |
| `pd.exe` 是壳不是加载器 | 要渲染输出、处理取消和交互，代码量比"一百行加载器"大得多 |
| 带 WebView2 运行时 | 盘上多约 180 MB，且要自己跟进版本 |
| 包脚本受限 | 有些"想直接跑个命令"的包写不了，得改成调业务命令 |
| 升级靠停内核后直接覆盖 | 拷一半断电就没救；建议覆盖前手动留一份 `.prev` |

## 18. 决策记录（为什么这么选）

| 决策 | 理由 |
|---|---|
| 微内核、功能皆扩展 | 想让每块都能换，核心保持小 |
| 客户端（壳）不是扩展 | 省掉一个进程和 stdio 转发；`Ctrl+C`、管道、`--json` 天然工作 |
| 命令静态声明在 `ext.json` | 内核不用叫醒扩展就能出 help；不会出现"扩展没启动所以命令不存在" |
| 命令表只在核心里，不下发客户端 | 客户端不会过期，也没有"schema 失配"分支；打错字由内核报错更自然 |
| 帮助/补全按需问 | 平时执行命令零额外开销；只有真用 help 或 Tab 才查一次 |
| 敲了命令才拉起扩展 | 命令表始终完整，扩展却只在用时才占内存 |
| 内核的管理命令也在同一张表 | `pd` 不需要特殊分支，所有命令一条路 |
| 存储做成扩展而不是内核 | 保住"唯一写者"，同时内核不用碰盘 |
| 租界由存储扩展发，不由内核发 | 内核连 store 在哪都不知道，才谈得上"不碰盘" |
| 用租界而不是逐文件授权 | 解压几万个文件，逐文件 IPC 不可接受 |
| 路径带哈希 | 路径即身份，避免同版本不同内容 |
| 两份哈希都存 | 能发现"装完之后被改过" |
| 不用开机自启 | 减少机器状态，符合"零残留" |
| 全部按需启动 | 简单、可预期；接受启动开销 |
| 包与扩展分开 | 概念清楚，权限也好分 |
| 包不带界面 | 界面是程序功能，不是工具内容 |
| 包脚本只跟 `pkgmgr` 说话，连不上内核 | 第三方代码，不该有内核连接资格；也省掉身份鉴别 |
| 不支持的能力拒绝整包 | 避免"装了一半"的中间态 |
| 每包独立回滚 | 批量操作时一个坏不影响其它 |
| 不做降级模式 | 砍掉一半分支，只承诺一种形态 |
| 接 Scoop 源 | 白拿一个生态，但先转成自己的格式 |
| 编排放在 `pkgmgr` 扩展 | 内核保持"不懂包"，换流程只改一处 |
| 控制面只传路径/句柄 | 几百 MB 的包不过内核，避免把守护进程拖死 |
| 包脚本与扩展分级 | 包可能来自第三方，不能给它和扩展一样的权限 |
| 每次请求带上下文快照 | 常驻进程的环境和用户终端不一样，不能让服务"猜" |
| 升级用"停内核再覆盖" | 比版本目录简单；代价是拷一半出错没退路 |
| store 路径用 16 位哈希 | 兼顾"路径即身份"和 Windows 260 字符限制；完整哈希存记录 |
| 核心扩展也允许用脚本 | 先保证能跑通，效率以后再说；慢几百毫秒可以接受 |
| download 与 unpack 不合并 | 各管一件事，换库/换实现互不影响 |
| 离线逐包判定 | `--offline` 只禁联网；内容在盘上就照装，不在就给出预取命令 |
| 独占 = 改机器或写盘 | `source add`、`fetch`、`index build` 也会写文件，必须排队；只读才并行 |
| 存档点存接线快照 | 不同版本可能设不同的环境变量，只记版本号推导不出来 |
| 进程管理做成 `proc` 扩展，不塞内核 | 内核保持"只自举"；进程机制可单独测试、替换；内核不碰 stdio 内容 |
| 进程等级三档、文案只在壳 | 机制层只产数据；换语言/改文案不动扩展；客户端不认识 code 也能回退 |
| 提权只做一次性实例，不做常驻 | 常驻管理员进程等于本地提权后门；一次性 UAC 可审计、可拒绝 |
| `pd proc` 命令归 `proc` 扩展，视图不合并 | 内核不碰业务进程、不当扩展能力调用方；统一展示是壳/窗口层的事 |
| 主题事件通道用通用机制（topic + subscribe） | 界面要实时刷新；通用通道一次到位，不给 `proc` 开特例 |
| `pd run` 由壳拉起而不是 proc | 代理 stdio 会破坏终端（TTY/Ctrl+C）；谁有终端谁负责 stdio |
